# OZON_PLATFORM

Версия: 1.1

Статус: Approved Draft

---

# 1. Назначение документа

Данный документ определяет архитектурные ограничения проекта.

Главная цель:

Сохранить проект простым, понятным и поддерживаемым на протяжении нескольких лет разработки.

Все разработчики, агенты ИИ и подрядчики обязаны соблюдать данный документ.

---

# 2. Главный принцип архитектуры

Простота важнее архитектурной красоты.

Если задачу можно решить:

* простым способом;
* сложным способом;

всегда выбирать простой способ.

---

# 3. Запрещено

Запрещается внедрять:

* DDD
* CQRS
* Event Sourcing
* Service Container
* Dependency Injection Framework
* Event Bus
* Microservices
* Repository Pattern без необходимости
* Factory Pattern без необходимости
* Plugin внутри Plugin

---

# 4. Основной подход

Проект должен состоять из минимального количества файлов.

Лучше:

5 понятных файлов

чем

50 файлов с абстракциями.

---

# 5. Этапность разработки

Разработка выполняется строго по этапам.

Этап 1

FREE

---

Этап 2

PRO

---

Этап 3

PORTAL

---

Запрещено:

разрабатывать PRO до завершения FREE.

Запрещено:

разрабатывать PORTAL до завершения PRO.

---

# 6. Изоляция проектов

Каждый проект имеет собственную область ответственности.

---

PROJECT A

FREE

Отвечает только за:

* Ozon API
* категории
* атрибуты
* публикацию товаров
* статусы

---

PROJECT B

PRO

Отвечает только за:

* лицензируемые функции
* очереди
* автоматизацию
* массовые операции

---

PROJECT C

PORTAL

Отвечает только за:

* лицензии
* платежи
* ЮKassa
* пользователей
* обновления

---

Запрещено смешивать зоны ответственности.

---

# 7. Правило новых функций

Перед добавлением новой функции необходимо определить:

1. В какой проект она относится.
2. Нужна ли она пользователю.
3. Приносит ли она доход.
4. Усложняет ли архитектуру.

Если функция не проходит проверку — она не реализуется.

---

# 8. Правило файлов

Каждый файл должен иметь понятное назначение.

Запрещено:

создавать файл "на будущее".

---

Разрешено:

создавать файл только при реальной необходимости.

---

# 9. Правило классов

Один класс = одна ответственность.

Примеры:

OzonClient

только API Ozon

---

LicenseClient

только лицензии

---

QueueManager

только очередь

---

Запрещено создавать классы вида:

MegaManager

SuperController

GlobalService

UniversalHelper

---

# 10. Правило зависимостей

Каждая новая зависимость требует обоснования.

Перед подключением библиотеки необходимо доказать:

* зачем она нужна;
* почему нельзя решить задачу штатными средствами.

---

# 11. WordPress First

Приоритет:

1. WordPress API
2. WooCommerce API
3. Собственный код

---

Запрещено:

создавать собственный механизм, если аналог уже существует в WordPress.

---

# 12. Очереди

Для всех длительных операций используется только:

Action Scheduler

---

Запрещено:

* собственные очереди;
* cron через while;
* ручное управление потоками.

---

# 13. Категории и атрибуты

Все данные должны поступать только из Ozon API.

Запрещено хранить:

* категории в коде;
* атрибуты в коде;
* обязательные поля в коде.

---

# 14. Хранение данных

Использовать только необходимые данные.

Запрещено:

сохранять данные без практической пользы.

---

# 15. Лицензирование

Логика лицензирования существует только в PORTAL.

---

FREE не содержит лицензирования.

---

PRO содержит только клиент лицензирования.

---

# 16. Обновления

FREE:

WordPress.org

---

PRO:

Update Server Portal

---

Логика обновлений должна быть отделена от бизнес-логики.

---

# 17. Логирование

Каждая ошибка должна быть журналирована.

Каждый журнал должен содержать:

* дату;
* действие;
* результат;
* текст ошибки.

---

# 18. База данных

Нельзя создавать таблицы без необходимости.

Приоритет:

1. post_meta
2. options
3. custom tables

---

Custom tables разрешены только при наличии реальной причины.

---

# 19. UI

Приоритет:

1. WooCommerce UI
2. WordPress UI
3. Собственный UI

---

Запрещено:

строить отдельную административную панель внутри WordPress без необходимости.

---

# 20. API

Каждый внешний API должен иметь отдельный клиент.

Примеры:

OzonClient

LicenseClient

YookassaClient

---

Запрещено смешивать API в одном классе.

---

# 21. Изменение архитектуры

Любое изменение архитектуры требует:

1. Обоснования.
2. Описания проблемы.
3. Предлагаемого решения.
4. Оценки последствий.

---

Без этих пунктов архитектура не изменяется.

---

# 22. Антихаос

Запрещено:

* переписывать работающий код без причины;
* массово переименовывать файлы;
* менять структуру проекта ради красоты;
* внедрять паттерны ради паттернов.

---

# 23. Главный критерий

Архитура считается правильной, если новый разработчик способен понять проект менее чем за один рабочий день.

---

# 24. Definition of Success

Успешная архитектура:

* понятна человеку;
* понятна OpenHands;
* легко поддерживается;
* легко расширяется;
* не требует постоянного рефакторинга.

---

# 25. Главный закон проекта

Если возникает спор между:

"красивой архитектурой"

и

"простым рабочим решением"

всегда выбирается простое рабочее решение.
