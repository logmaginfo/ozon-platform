# OZON_PLATFORM

# 1. Назначение документа

Документ определяет единые стандарты кодирования для всех компонентов платформы:

* FREE Plugin
* PRO Plugin
* License Portal

Все разработчики и ИИ-агенты обязаны соблюдать данные правила.

---

# 2. Главный принцип

Код должен быть:

1. Понятным
2. Предсказуемым
3. Поддерживаемым

---

Запрещено писать код:

* ради красоты;
* ради паттернов;
* ради демонстрации навыков.

---

# 3. Приоритет стандартов

Порядок приоритета:

1. Данный документ
2. WordPress Coding Standards
3. WooCommerce Standards
4. PHP Standards

---

# 4. Стандарты FREE и PRO

Основной язык:

PHP 8+

---

Frontend:

JavaScript

jQuery (разрешено)

---

Стили:

CSS

---

Запрещено подключать frontend-фреймворки без отдельного решения.

---

# 5. Именование файлов

Используется формат:

```text
class-ozon-client.php
class-product-export.php
class-license-client.php
```

---

Запрещено:

```text
client.php

new.php

helper.php

utils.php

temp.php
```

---

Название должно отражать назначение.

---

# 6. Именование классов

Формат:

```php
class Ozon_Client
{
}
```

---

Примеры:

```php
class Ozon_Client
class Ozon_Category_Manager
class Product_Exporter
class License_Client
```

---

Запрещено:

```php
class Manager
class Service
class Helper
class Utils
class Main
```

---

# 7. Именование методов

Формат:

```php
public function get_categories()
{
}
```

---

Примеры:

```php
get_categories()

sync_products()

check_status()

create_license()
```

---

Запрещено:

```php
doWork()

run()

process()

handle()
```

если название не отражает действие.

---

# 8. Размер методов

Рекомендуемый размер:

до 50 строк.

---

Если метод превышает:

100 строк

необходимо рассмотреть разделение.

---

# 9. Размер классов

Рекомендуемый размер:

до 500 строк.

---

Если класс превышает:

1000 строк

необходимо провести аудит.

---

# 10. Комментарии

Комментарии должны объяснять:

ПОЧЕМУ

а не

ЧТО

---

Плохо:

```php
// Получаем категории
$categories = ...
```

---

Хорошо:

```php
// Ozon требует актуальный список категорий,
// поэтому данные обновляются через API.
```

---

# 11. Логирование

Все ошибки логируются.

Минимальный набор данных:

* дата;
* операция;
* результат;
* сообщение ошибки.

---

Пример:

```php
$this->logger->error(
    'Export failed',
    [
        'product_id' => $product_id,
        'error' => $message,
    ]
);
```

---

# 12. Исключения

Запрещено:

```php
catch ( Exception $e ) {
}
```

---

Исключение должно:

* логироваться;
* обрабатываться.

---

# 13. Работа с базой данных

Приоритет:

1. WooCommerce API
2. WordPress API
3. SQL

---

Запрещено писать SQL если существует штатный API.

---

# 14. Работа с метаданными

Метаполя должны иметь префикс:

```text
_ozon_
```

---

Примеры:

```text
_ozon_status

_ozon_task_id

_ozon_last_upload

_ozon_error
```

---

# 15. Работа с API

Каждый внешний API имеет собственный клиент.

---

Примеры:

```php
Ozon_Client

License_Client

Yookassa_Client
```

---

Запрещено смешивать API.

---

# 16. Работа с AJAX

Каждое действие:

отдельный обработчик.

---

Запрещено:

создавать универсальные AJAX-контроллеры.

---

# 17. Работа с JavaScript

JavaScript отвечает только за:

* интерфейс;
* AJAX;
* UX.

---

Бизнес-логика находится только в PHP.

---

# 18. Безопасность

Каждый запрос обязан проверять:

```php
nonce
```

---

Каждый ввод обязан проходить:

```php
sanitize_text_field()
```

или соответствующую обработку.

---

Каждый вывод обязан использовать:

```php
esc_html()

esc_attr()

esc_url()
```

---

# 19. Action Scheduler

Для длительных операций использовать только:

Action Scheduler.

---

Запрещено:

* собственные очереди;
* бесконечные циклы;
* ручные таймеры.

---

# 20. Документирование изменений

Каждое изменение должно сопровождаться:

* описанием задачи;
* списком измененных файлов;
* описанием результата.

---

# 21. Стиль работы OpenHands

Перед написанием кода агент обязан:

1. Изучить документацию.
2. Изучить архитектуру.
3. Найти затрагиваемые файлы.
4. Подготовить план.

Только после этого писать код.

---

# 22. Формат ответа OpenHands

Каждая задача оформляется в формате:

1. Что делаем.
2. Какие файлы меняем.
3. Полный код.
4. Что проверить.
5. Следующий шаг.

---

# 23. Запрещено

Запрещено:

* писать псевдокод;
* писать неполные методы;
* оставлять TODO;
* оставлять заглушки;
* создавать мертвый код;
* создавать код "на будущее".

---

# 24. Definition of Good Code

Хороший код:

* читается без комментариев;
* имеет понятные названия;
* решает одну задачу;
* не содержит лишних абстракций.

---

# 25. Главный закон кодирования

Через 12 месяцев владелец проекта должен открыть любой файл и понять его назначение менее чем за 5 минут.
