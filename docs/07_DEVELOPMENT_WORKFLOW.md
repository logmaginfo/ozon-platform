# 07_DEVELOPMENT_WORKFLOW.md

# OZON_PLATFORM

Версия: 1.1

Статус: Approved Draft

---

# 1. Назначение документа

Документ определяет единый процесс разработки для:

* OpenHands
* Claude Code
* Cursor
* Devin
* разработчиков

Цель:

Обеспечить предсказуемый и контролируемый процесс разработки.

---

# 2. Главный принцип

Запрещено писать код сразу после получения задачи.

Каждая задача проходит полный цикл:

Анализ
↓
План
↓
Согласование
↓
Код
↓
Тестирование
↓
Документация
↓
Коммит

---

# 3. Обязательное чтение

Перед началом работы агент обязан изучить:

01_PRODUCT_CHARTER.md

02_BUSINESS_MODEL.md

03_ARCHITECTURE_RULES.md

04_REPOSITORY_STRUCTURE.md

05_ANTI_CHAOS_SYSTEM.md

06_CODING_STANDARDS.md

---

Если документация не прочитана:

работа запрещена.

---

# 4. Этап 1 — Анализ задачи

После получения задачи агент обязан определить:

* что требуется сделать;
* к какому проекту относится задача;
* какие файлы затрагиваются;
* какие риски существуют.

---

Запрещено:

сразу предлагать код.

---

# 5. Формат анализа

Анализ обязан содержать:

Что нужно сделать.

---

Какие файлы будут изменены.

---

Какие данные будут использоваться.

---

Какие риски существуют.

---

# 6. Этап 2 — Планирование

После анализа создается план.

Формат:

Шаг 1

Шаг 2

Шаг 3

Шаг 4

---

План должен быть понятен владельцу проекта.

---

# 7. Этап 3 — Согласование

До подтверждения владельцем:

код писать запрещено.

---

Разрешено:

* анализ;
* обсуждение;
* архитектурные предложения.

---

# 8. Этап 4 — Реализация

После подтверждения плана разрешено писать код.

---

Код должен:

* соответствовать архитектуре;
* соответствовать Coding Standards;
* соответствовать текущему этапу проекта.

---

# 9. Формат ответа при реализации

Каждая задача оформляется одинаково.

---

1. Что делаем

---

2. Какие файлы изменяем

---

3. Полный код

---

4. Что проверить

---

5. Следующий шаг

---

Исключения запрещены.

---

# 10. Полный код

Если изменяется метод:

выводится полный метод.

---

Если изменяется класс:

выводится полный класс.

---

Запрещено:

```text id="e3q8d1"
...
оставшийся код без изменений
...
```

---

Запрещено:

неполные примеры.

---

# 11. Запрет на догадки

Если информации недостаточно:

агент обязан задать вопрос.

---

Запрещено:

додумывать структуру проекта.

---

Запрещено:

создавать файлы, которых нет.

---

# 12. Работа с существующим кодом

Перед изменением файла агент обязан:

* прочитать файл;
* понять назначение файла;
* определить взаимосвязи.

---

Только после этого разрешено изменение.

---

# 13. Минимальные изменения

Изменяется только необходимый код.

---

Запрещено:

* случайное форматирование;
* лишний рефакторинг;
* изменение несвязанных участков.

---

# 14. Работа с ошибками

При обнаружении ошибки агент обязан:

1. Найти причину.
2. Описать причину.
3. Предложить исправление.
4. Только затем писать код.

---

# 15. Работа с архитектурой

Если задача требует изменения архитектуры:

создается документ:

ARCHITECTURE_CHANGE_REQUEST

---

Без него изменение запрещено.

---

# 16. Работа с базой данных

Перед изменением структуры данных агент обязан определить:

* влияние на совместимость;
* влияние на обновления;
* влияние на миграции.

---

# 17. Работа с API

Перед изменением API агент обязан проверить:

* совместимость;
* обратную совместимость;
* существующие интеграции.

---

# 18. Работа с документацией

После реализации обновляются:

* Product Docs
* Changelog
* Roadmap

---

Если документация не обновлена:

задача считается незавершенной.

---

# 19. Работа с Git

Каждая задача:

отдельная ветка.

---

Каждая задача:

отдельный коммит.

---

Запрещено объединять несколько задач в один коммит.

---

# 20. Формат коммитов

Примеры:

```text id="m4p0k2"
Add category sync

Add product export

Add license validation

Fix status checking
```

---

Запрещено:

```text id="w0s8z9"
fix

update

changes

work
```

---

# 21. Тестирование

Перед завершением задачи агент обязан проверить:

* основной сценарий;
* негативный сценарий;
* обработку ошибок.

---

# 22. Проверка документации

Перед завершением задачи агент обязан убедиться:

что документация соответствует текущему состоянию проекта.

---

# 23. Контроль контекста

Перед каждой новой задачей агент обязан:

повторно проверить актуальную документацию.

---

Запрещено полагаться на память предыдущих задач.

---

# 24. Работа OpenHands

OpenHands обязан работать по схеме:

Прочитал документацию
↓
Проанализировал задачу
↓
Создал план
↓
Получил подтверждение
↓
Написал код
↓
Обновил документацию
↓
Создал коммит

---

# 25. Контроль владельца

Владелец проекта имеет право:

* отклонить решение;
* потребовать альтернативу;
* остановить реализацию;
* изменить приоритет задачи.

---

# 26. Definition of Success

Процесс разработки считается правильным если:

* OpenHands не теряет контекст;
* изменения предсказуемы;
* каждая задача контролируется;
* документация всегда актуальна;
* проект развивается без хаоса.

---

# 27. Главный закон разработки

Ни одна строка кода не должна появляться в проекте без понимания:

зачем она нужна,

какую проблему решает,

и как повлияет на систему в целом.
